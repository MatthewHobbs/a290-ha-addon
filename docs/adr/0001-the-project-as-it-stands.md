# ADR 0001 — The add-on as it stands

- **Repo:** a290-ha-addon
- **Status:** Accepted (2026-10-25). A retrospective: every decision below is read from the code, the workflows and the scripts as they are at `297b6b1`, and nothing in it is new. It replaces the earlier records, which are gone.
- **Context:** this repository is a Home Assistant add-on for the Alpine A290. It polls the Renault Kamereon API for one car and publishes what it finds to Home Assistant over MQTT. Others install it, so what it does with a credential, a location or a failure matters more than how much it exposes. A sibling repo, `r5-ha-addon`, is the Renault 5 port of the same code.
- **North star:** the add-on tells the truth about the car, or says it does not know. It never invents a fresh reading, never ships a control the car refuses, never lets a secret or a precise location leave the machine unmasked, and never installs a release that was not booted first.

## Decision

One add-on, one car, one poll loop, published as discovered MQTT entities, with every claim about the car gated on what the car says it supports and every failure shown as a failure. The runtime is small and its checks are many, because it runs unattended in other people's homes.

## Context

The A290 is one of two Renault-group cars reachable through the same Kamereon API, and the library that talks to it, `renault-api`, keeps a hard-coded map of which endpoints each model exposes. That map, not the library's documentation, decides what this car can do, which is why rows 4 and 19 treat support as something to probe and pin and not something to assume. The A290 refuses several endpoints, accepts others only under conditions (Start Charging acts by clearing the car's own timer, so it does nothing for someone whose charging is scheduled elsewhere), and sometimes answers a location request with a value that means no fix. Most of the rows above exist because of one of those three facts.

The add-on runs as root inside a container it does not control, holds a credential to a car and, if allowed, that car's location. It also shares a repository that is public. That is why rows 11, 12, 18 and 20 are as strict as they are.

## Consequences

- The runtime stays small on purpose. A new reading is a catalogue row and a poll line; a new control is a catalogue row and a gated command. Anything that needs a decision about the car's behaviour belongs here as a row first.
- The shared core is a pinned commit of another repository. A fix there does not reach this add-on until `CORE_REF` moves, and nothing bumps it automatically (row 26).
- Everything in the table is checked by something that can fail, except where a row says otherwise: the tag run in row 25 has not yet run on a real release, and row 27 is open.
- **Not established:** how this add-on behaves on a real A290 for the endpoints I have not seen refuse or accept, beyond what the tests and the changelog record; that the Supervisor on a user's host acts on the image `HEALTHCHECK`; and any behaviour of the shared core that the add-on's own tests do not exercise.
